# Раздел конфигурации `[fork]`

Всё, что этот форк добавляет поверх telemt, настраивается в `[fork]` и больше
нигде. Отсюда два следствия, ради которых раздел и сделан:

- **Конфиг, написанный для оригинального telemt, сохраняет ровно тот же
  смысл.** Ни один ключ вне `[fork]` не ведёт себя иначе из-за того, что это
  форк, поэтому `config.toml` от telemt 3.5.5 можно положить как есть.
- **Удаление `[fork]` оставляет рабочий прокси.** Любая функция форка доступна
  только через этот раздел, а `[fork] enabled = false` выключает всё одним
  ключом.

Раздел необязателен. Его отсутствие сохраняет поведение, которое у форка было
всегда, потому что каждый переключатель по умолчанию включён.

## Верхний уровень

| Ключ | Тип | По умолчанию | Значение |
| --- | --- | --- | --- |
| `enabled` | bool | `true` | Главный выключатель. `false` заставляет процесс вести себя как оригинальный telemt: все переключатели ниже читаются как выключенные, а WEB-транспорт форка, панель, бот и bulk API не поднимаются независимо от их собственных `enabled`. |
| `web_implementation` | string | `"auto"` | Какая реализация WEB-прокси работает: `auto`, `telemt`, `fork`, `both`, `off`. См. [ниже](#какая-реализация-web-прокси-работает). |

При `enabled = false` остальная часть раздела остаётся на диске: написанные
оператором ключи сохраняются и видны в `GET /v1/config`, но не действуют.
Именно это делает выключатель пригодным для того, чтобы отделить изменение
форка от поведения апстрима, ничего больше не правя.

## `[fork.runtime]` — поведение рантайма

По одному булеву значению на каждое отличие от оригинального telemt, все по
умолчанию `true`. Значение `false` возвращает то, что делает telemt. Все они
читаются при старте или при перезагрузке рантайма, поэтому изменение требует
runtime reload, а не горячего применения конфига.

| Ключ | Включено | Выключено (поведение telemt) |
| --- | --- | --- |
| `process_admission_budget` | Один семафор соединений на процесс, перенастраивается на месте. | Каждое поколение создаёт свой, поэтому drain-перезагрузка допускает до двух `server.max_connections` одновременно. |
| `process_buffer_pool` | Один пул буферов реле на процесс. | Каждое поколение выделяет свой, удваивая занятую память на время drain. |
| `process_uptime_clock` | `telemt_uptime_seconds` считает время процесса. | Перезагрузка сбрасывает счётчик в ноль. |
| `reload_cancel` | `DELETE /v1/system/reload/{id}` отменяет перезагрузку. | Долгий drain держит единственный слот до конца; оба пути отправки отвечают 409. |
| `reload_deadlines` | Подготовка, quiesce и ожидание команды при завершении ограничены по времени. | Эти шаги повторяются без предельного срока, и зависшая подготовка превращает SIGTERM в SIGKILL. |
| `reload_config_rollback` | `failure_policy = "rollback"` восстанавливает файл конфига с проверкой ревизии. | Отбрасывается только кандидат рантайма; новый конфиг остаётся на диске и применяется наблюдателем. |
| `reload_validate_candidate` | Кандидат перезагрузки проходит `ProxyConfig::validate()`. | Работают только внутренние проверки загрузчика, поэтому перезагрузка может установить конфиг, фатальный при старте. |
| `reload_error_kind` | В статусе перезагрузки есть стабильный слаг `error_kind`. | Форма telemt: только сообщение. |
| `reload_config_snapshot_hash` | Наблюдатель нового поколения инициализируется снимком, из которого собрана перезагрузка. | Наблюдатель перечитывает файл при старте и теряет запись, попавшую в окно подготовки. |
| `me_writer_teardown` | Задачи писателей Middle-End отменяются, сокеты закрываются. | Писателям только подаётся сигнал, их соединения накапливаются между перезагрузками. |
| `tls_front_cache_budget_release` | Отставленный TLS-front кеш возвращает свои резервации в счётчик процесса. | Счётчик растёт до отказа всем адресам. |
| `synlimit_generation_reconciler` | Правила SYN-лимитера пересогласуются при смене поколения и горячей перезагрузке. | Правила согласуются один раз при старте. |
| `shutdown_unbind_listeners_first` | Слушающие сокеты закрываются первым действием при завершении. | Слушатели останавливаются поздно, и порт всё окно завершения продолжает завершать TCP-хендшейки и сбрасывать их. |
| `session_admission_closed_metric` | Экспортируется `telemt_session_admission_closed_total`. | Метрики нет. |
| `user_delete_forgets_quota` | Квота и статистика удалённого пользователя сбрасываются. | Пользователь с тем же именем создаётся уже с потраченной квотой. |
| `rust_log_survives_reload` | `RUST_LOG` оператора переживает перезагрузку. | Перезагрузка выводит фильтр только из `general.log_level`. |

## `[fork.web]` — WEB-транспорт форка

Полный справочник —
[docs/Advanced_settings/WEB_PROXY.en.md](../Advanced_settings/WEB_PROXY.en.md).
Схема не изменилась с тех пор, как этот транспорт занимал `[web]`; переехало
только имя раздела: `enabled`, `listen`, `admin_listen`, `hostname`,
`public_dir`, `public_upstream`, `carrier_mode`, `derive_user_profiles`,
`trusted_proxies`, `limits`, `timeouts`, `profiles`.

## `[fork.prometheus]` — встроенная панель

Один самодостаточный HTML-документ рядом с той же экспозицией, которую процесс
уже отдаёт. Ни одной внешней ссылки: страница читает `/metrics` со своего же
origin и рисует всё в браузере, поэтому работает на хосте без исходящей сети.

| Ключ | Тип | По умолчанию | Значение |
| --- | --- | --- | --- |
| `enabled` | bool | `false` | Отдавать панель. |
| `path` | string | `"/panel"` | Путь документа. Не должен перекрывать `/metrics` и `/beobachten`. |
| `listen` | string | `""` | Отдельный слушатель `ip:port`. Пусто — панель живёт на слушателе метрик. |
| `whitelist` | list | loopback | Сети, которым разрешён отдельный слушатель. При пустом `listen` не используется. |
| `refresh_secs` | int | `5` | Период опроса в браузере. |
| `history_points` | int | `120` | Сколько точек на серию хранит браузер. Максимум 1440. |
| `title` | string | `""` | Заголовок. Пусто — имя продукта и версия. |
| `show_users` | bool | `false` | Показывать строки по пользователям: в этих сериях имена пользователей идут метками. |

При пустом `listen` панель наследует `server.metrics_whitelist` и бюджет
соединений слушателя метрик. Отдельный `listen` нужен там, где страница должна
быть доступна с рабочей станции, а `/metrics` и `/beobachten` — нет.

## `[fork.telegram]` — бот администратора

Задача уровня процесса: long-poll Bot API и фиксированный набор команд поверх
того же control plane, через который пишет HTTP API.

| Ключ | Тип | По умолчанию | Значение |
| --- | --- | --- | --- |
| `enabled` | bool | `false` | Запускать бота. |
| `token` | string | `""` | Токен от @BotFather. Файл конфига следует считать секретом. |
| `admins` | list of int | `[]` | Telegram id, которым разрешено писать боту. Здесь должны быть и отправитель, и чат: для личного чата достаточно одного user id, для группы нужен ещё её (отрицательный) chat id. Обязателен при включении. |
| `allow_mutations` | bool | `false` | Разрешает команды, меняющие конфигурацию. |
| `api_base` | string | `"https://api.telegram.org"` | Origin Bot API, для собственного Bot API сервера. |
| `poll_timeout_secs` | int | `25` | Таймаут long-poll. 1..=50. |
| `request_timeout_secs` | int | `30` | Таймаут запроса. Должен быть больше `poll_timeout_secs`. |
| `upstream_scope` | string | `""` | Scope из `[[upstreams]]`, через который идёт трафик самого бота. Пусто — прямое соединение с Bot API. |

Команды: `/status`, `/users`, `/links <user>` — только чтение;
`/adduser`, `/deluser`, `/enable`, `/disable`, `/rotate` — требуют
`allow_mutations`.

Два момента до включения:

- **В списке администраторов должны быть и отправитель, и чат**; сообщение, не
  прошедшее любую из проверок, отбрасывается без ответа. Проверки одного
  отправителя мало: администратор написал бы `/rotate alice` в общей группе, и
  бот отправил бы новый секрет всем её участникам. Поэтому использование в
  группе — осознанное решение: её отрицательный chat id добавляется в `admins`.
- **Трафик Bot API идёт напрямую, пока не задан `upstream_scope`.** Изоляция
  сделана намеренно: клиентский трафик ходит через upstreams без scope, и
  недоступный Bot API иначе пометил бы их нездоровыми после нескольких неудачных
  опросов — прокси деградировал бы из-за неработающей интеграции с чатом. На
  хосте, которому нужен egress, задайте `upstream_scope` и укажите то же
  значение в `scopes` у соответствующего `[[upstreams]]`: выбираются только
  upstreams с этим scope, поэтому их отказы остаются на них.

## `[fork.api]` — bulk-запросы

`POST /v1/bulk` применяет много операций над пользователями за одну загрузку
конфига, одну запись и один набор действий над рантаймом. Одиночные маршруты
тратят все три на каждую операцию, и каждая запись обесценивает ревизию
вызывающего для следующего запроса.

| Ключ | Тип | По умолчанию | Значение |
| --- | --- | --- | --- |
| `bulk_enabled` | bool | `false` | Отдавать маршрут. |
| `bulk_max_operations` | int | `100` | Сколько операций несёт один пакет. Максимум 1000. |
| `bulk_timeout_secs` | int | `10` | Бюджет времени на пакет. Должен быть меньше 15-секундного дедлайна соединения API, то есть 1..=14. |

```json
{
  "atomic": true,
  "operations": [
    { "id": "1", "action": "user.create", "body": { "username": "alice" } },
    { "id": "2", "action": "user.patch", "user": "bob", "body": { "data_quota_bytes": 1073741824 } },
    { "id": "3", "action": "user.disable", "user": "carol" },
    { "id": "4", "action": "user.rotate_secret", "user": "dave" },
    { "id": "5", "action": "user.delete", "user": "erin" }
  ]
}
```

`atomic` по умолчанию `true`: одна отклонённая операция отменяет весь пакет,
ничего не записывается, ответ — `409` со списком результатов по операциям. При
`atomic = false` корректные операции применяются, отклонённые перечисляются.
`If-Match` проверяется один раз на весь пакет.

Тела операций — те же формы, что принимают одиночные маршруты, поэтому
`user.patch` сохраняет трёхзначную семантику `PATCH /v1/users/{user}`:
отсутствующее поле не меняется, `null` удаляет его. `user.enable` удаляет ключ
из `access.user_enabled`, а не пишет `true`, и `user.rotate_secret` не рвёт
живые сессии — и то и другое совпадает с одиночными маршрутами.

Одно ограничение стоит знать до разнесения конфига по include-файлам: пакет
пишет все затронутые таблицы `access.*` в **один** файл, поэтому если они
принадлежат разным include, пакет отвергается с `409 config_patch_not_atomic` и
ничего не записывается. Те же операции по одной прошли бы, потому что каждая
трогает меньше таблиц. Пакет с `user.delete` от этого не страдает — эта
операция и так пишет все восемь таблиц любым маршрутом, — а вот пакет,
смешивающий, скажем, создание с патчем таблицы квот из отдельного include,
страдает. Держите таблицы `access.*` в одном файле или разбивайте такой пакет по
файлам.

## Какая реализация WEB-прокси работает

В этом бинарнике две реализации WEB-прокси. Они говорят на одном опубликованном
протоколе и не делят больше ничего:

| | telemt | этот форк |
| --- | --- | --- |
| Настраивается в | `[web]` | `[fork.web]` |
| Слушатель | запись `[[server.listeners]]` с `transport = "web"` | собственный `listen` |
| Терминация потока | в процессе | в процессе или loopback MTProxy |
| Публичный сайт | decoy на каждый vhost | `public_dir` или `public_upstream` |

`fork.web_implementation` решает, что именно запускается: `auto` — то, что
включено остальной конфигурацией (обе, если настроены обе); `telemt` —
только telemt, `[fork.web] enabled = true` отвергается; `fork` — только форк,
слушатель `transport = "web"` отвергается; `both` — обе; `off` — ни одной, и
конфигурация, которая просит транспорт, отвергается.

Противоречие — ошибка загрузки, а не тихое переопределение: тихое
переопределение — это как раз тот отказ, которого оператор не видит, потому что
юнит остаётся зелёным, а настроенный транспорт не поднимается.

## Обновление конфига, написанного до `[fork]`

До того как в telemt появился свой WEB-транспорт, `[web]` целиком принадлежал
форку. Существующий конфиг править не нужно: таблица `[web]`, написанная по
схеме форка, распознаётся на сыром документе, переносится в `[fork.web]`, и в
лог пишется предупреждение об устаревании. Переименование раздела убирает
предупреждение.

Схемы делят только `enabled`, `limits` и `timeouts`; любой другой ключ
принадлежит ровно одной из них, поэтому решение принимается по ключам, которые
не могут встретиться в обеих. `[web]`, смешивающий ключи обеих схем,
отвергается с перечислением обоих списков: угадывать здесь значит поднять не
тот транспорт.

## Что не переключается

У трёх отличий форка выключателя нет, потому что «выключено» для них означало
бы вернуть удалённый код, а не пойти другой веткой:

- единственный на процесс контроллер буферов Direct и его envelope;
- `dns_overrides` уровня поколения — глобальной таблицы процесса больше нет, а
  снимок передаётся явным параметром везде, где происходит резолв;
- страховка `Drop` у reload-тикета, которая завершает статус перезагрузки, если
  ранний возврат иначе заклинил бы API на 409 до конца жизни процесса.

Идентификация продукта тоже не переключается: TELEMT PUBLIC LICENSE 3.3 §3
требует, чтобы изменённая сборка обозначала себя как неофициальную, поэтому
`--version`, `telemt_build_info` и `GET /v1/system/info` всегда сообщают о
форке.
