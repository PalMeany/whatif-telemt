# WhatIf Telemt

**WhatIf Telemt — это неофициальная, изменённая версия [Telemt](https://github.com/telemt/telemt). Проект не аффилирован с проектом Telemt и его сопровождающими, не одобрен и не поддерживается ими.**

MTProto-прокси на Rust и Tokio. Форк <https://github.com/telemt/telemt> от коммита `d851200` (telemt 3.4.25), развивающийся независимо с этого момента.

[README in English](README.md)

## Что это

Вышестоящий Telemt реализует официальный протокол MTProto-прокси Telegram и
большой набор возможностей поверх него. Этот форк наследует всё это целиком и
существует ради остального: того, чего в вышестоящем проекте нет, ещё не
добавили или не добавят никогда. Изменения появляются здесь, когда их полезно
запускать в продакшене и нет причин ждать, пока они появятся где-то ещё.

Унаследовано от апстрима (форк сейчас несёт telemt 3.5.5) и принадлежит проекту Telemt: режимы MTProto
(classic, secure с префиксом `dd`, fake-TLS с префиксом `ee` и SNI-fronting),
TLS-fronting, Middle-End Pool, защита от replay-атак, маскировка, квоты и
пользовательские лимиты, Control API и метрики.

Добавлено здесь; полное описание — в
[CHANGES-FROM-UPSTREAM.md](CHANGES-FROM-UPSTREAM.md):

- **транспорт WEB-прокси** — MTProto внутри WebView, принадлежащего приложению,
  поверх носителя, который выглядит как обычный HTTPS-сайт; поток завершается
  внутри процесса, а не передаётся отдельному MTProxy по loopback TCP;
- **соответствие протоколу и устойчивость** этого транспорта: любой отказ
  неотличим от обычного «404» по телу ответа, заголовкам, времени и состоянию
  соединения; документ моста закреплён по SHA-256 против эталонного носителя;
  бюджеты кадров, полосы носителя, живучесть WebSocket и перезагрузка профилей
  покрыты тестами;
- **встроенная веб-панель** — интерфейс оператора, вкомпилированный в бинарник:
  роли, второй фактор, журнал аудита с цепочкой хэшей и подписанная федерация
  узлов, позволяющая одному серверу управлять остальными;
- **инструменты развёртывания**: пошаговый рунбук, шаблоны фронт-прокси для
  Caddy и nginx, Dockerfile для сборки из исходников и неинтерактивный
  установщик;
- **усиление подсистемы перезагрузки конфигурации**, появившейся в 3.4.25:
  ревизия показала, что она была доведена не до конца;
- **раздел конфигурации `[fork]`**, которому принадлежит всё перечисленное
  выше: конфиг, написанный для оригинального telemt, сохраняет здесь прежний
  смысл, а `[fork] enabled = false` выключает весь форк одним ключом
  ([docs/Fork/FORK_CONFIG.ru.md](docs/Fork/FORK_CONFIG.ru.md));
- **встроенная панель Prometheus**, **Telegram-бот администратора** и
  **bulk-запросы к API** — всё выключено по умолчанию и настраивается в
  `[fork]`.

С момента форка вышестоящий проект развивается независимо и находится в ветке
3.5.x. Кодовые базы разошлись, и наличие возможности в одной из них не означает
её наличия в другой: в вышестоящей ветке 3.5.x есть собственная, написанная
отдельно реализация WEB-прокси. В этой сборке присутствуют обе, а
`fork.web_implementation` выбирает, какая из них работает. О проблемах этого
форка сообщайте сюда, а не в проект Telemt.

Собранный бинарник представляется именно как этот форк:

```console
$ telemt --version
WhatIfTelemt 3.5.5.1w
```

## Транспорт WEB-прокси

Полный справочник (на английском):
[docs/Advanced_settings/WEB_PROXY.en.md](docs/Advanced_settings/WEB_PROXY.en.md).

Клиент Telegram с поддержкой WEB сохраняет обычный формат кадров и шифрование
MTProxy, но проводит каждое соединение с прокси через один WebView,
принадлежащий приложению, вместо прямого TCP. WebView поднимает
same-origin-носитель поверх HTTPS или WebSocket на хосте, который для всякого,
кто не может аутентифицироваться, выглядит обычным HTTPS-сайтом: по любому пути
отдаётся сайт оператора, и только `GET /?bridge=<действительная capability>`
возвращает что-то иное.

Транспорт реализует клиентонезависимый контракт протокола
[`telegramdesktop/tproxy-server`](https://github.com/telegramdesktop/tproxy-server)
(WEB proxy protocol v1), поэтому любой клиент, говорящий на этом протоколе,
работает с этим релеем без изменений. Происхождение материала, заимствованного
из того проекта, описано в [NOTICE.md](NOTICE.md).

```text
Интернет :443 -> TLS-фронт-прокси (Caddy/nginx) -> 127.0.0.1:8080 носитель WEB
                                                     |
                                                     +-> конвейер MTProto-клиента внутри процесса
                                                     +-> сайт оператора (в памяти или приложение на loopback)
```

Эталонный релей передаёт каждый демультиплексированный поток обычному MTProxy по
loopback-соединению TCP. Здесь поток завершается **внутри процесса**: байты
попадают в тот же конвейер, которым пользуется прямой TCP-клиент, поэтому
WEB-клиент получает обработку fake-TLS, маршрутизацию через Middle-End,
пользовательские лимиты, квоты, учёт IP, статистику и маскировку ровно так же,
как любой другой клиент — и при этом на каждый фрагмент приходится на два
системных вызова и две копии в ядре меньше. Loopback-бэкенд остаётся доступен
(`backend = "127.0.0.1:2398"`) для развёртываний, которым нужен отдельный
процесс MTProxy.

### Режимы носителя

| Режим | Устройство | Компромисс |
| --- | --- | --- |
| `https` | Один последовательный аплинк и один long-poll-даунлинк | Самый простой; загруженное направление ограничено примерно `carrier_batch_bytes / RTT` |
| `https-lanes` | Отдельная полоса запросов на каждый логический поток | Снимает head-of-line blocking носителя; требует HTTP/2 на публичном origin |
| `websocket` | Один мультиплексированный WebSocket | Снимает ограничение «стой-и-жди»; нет изоляции между потоками |
| `websocket-lanes` | Отдельный WebSocket на каждый логический поток | Лучшая изоляция; больше сокетов и TLS-рукопожатий на сессию |

Режим фиксируется при создании сессии и зашивается в страницу моста, поэтому при
смене режима оператором клиенту не нужны новые настройки.

**Используйте `https`.** Все четыре режима реализованы и покрыты тестами, но в
протоколе v1 нет согласования носителя, и ни один выпущенный клиент не был
замечен за работой через WebSocket-носитель (по состоянию на август 2026).
Режим, который клиент не умеет вести, ломается незаметно: сессия создаётся,
счётчики растут, а клиент бесконечно висит на «подключении». Релей называет
затронутые профили при запуске, вместо того чтобы выдавать это за исправно
работающий носитель.

### Что нужно знать оператору до развёртывания

- **Нужен фронт-прокси с терминацией TLS.** Страница моста должна забираться по
  настоящему HTTPS с публично доверенным сертификатом для настроенного хоста.
  Публичен только фронт-прокси; слушатели носителя (`listen`) и служебный
  (`admin_listen`) остаются на loopback, а носитель по замыслу работает по
  открытому HTTP. Порт 443 принадлежит фронт-прокси, поэтому прямому слушателю
  MTProto нужен другой порт или другой адрес.
- **`web.hostname` — это имя, которое клиенты вводят в приложении**, потому что
  capability моста считается как `HMAC(secret, "…\n" + hostname)`: релей и
  клиент должны вывести её по одному и тому же имени.
- **Клиент настраивает только хост и обычный секрет MTProxy.** Capability
  выводится локально:
  `base64url-no-padding(HMAC-SHA256(secret, "tdesktop-web-proxy-bridge-v1\n" + hostname))`,
  что даёт `https://<hostname>/?bridge=<capability>`.
- **Секреты fake-TLS (`ee`) через этот транспорт не работают** — WEB-клиент их
  не принимает, — поэтому для WEB-пользователей включайте `classic` или `secure`
  в `[general.modes]`, а прямым клиентам выдавайте `ee`-ссылку отдельно.
- **Публичный сайт предоставляет оператор.** Здесь он не генерируется: стартовая
  страница, общая для многих операторов, сама по себе является признаком при
  активном зондировании.

## Сборка

Rust edition 2024, актуальный стабильный тулчейн. В release-профиле включён
fat LTO, поэтому сборке нужно около 2 ГБ ОЗУ и несколько минут.

```bash
git clone https://github.com/PalMeany/whatif-telemt.git
cd whatif-telemt
cargo build --release --locked
./target/release/telemt --version        # WhatIfTelemt 3.5.5.1w
./target/release/telemt config.toml      # запуск на переднем плане
```

Тесты: `cargo test` (в CI выполняются `cargo fmt -- --check`, `cargo clippy` и
`cargo nextest run`).

Образ, собираемый из этого рабочего дерева, — для хостов, где тулчейн не нужен:

```bash
docker build -f contrib/web/Dockerfile.source -t whatif-telemt:local .
```

### Готовых сборок для скачивания пока нет

`install.sh`, корневой `Dockerfile` и `docker-compose.yml` — это унаследованные
от вышестоящего проекта инструменты, перенаправленные на этот репозиторий: они
скачивают release-архив или контейнерный образ из `PalMeany/whatif-telemt`. Этот
форк не публикует ни того, ни другого, поэтому ни один из этих путей сейчас его
не установит; установка одной командой из унаследованной
[инструкции по быстрому запуску](docs/Quick_start/QUICK_START_GUIDE.ru.md)
не работает по той же причине. Собирайте из исходников или пользуйтесь
установщиком для WEB, описанным ниже.

## Установка с транспортом WEB

[`install-web.sh`](install-web.sh) автоматизирует шаги 2–10 рунбука
[contrib/web/DEPLOY.md](contrib/web/DEPLOY.md) на чистом хосте Debian или Ubuntu
с systemd: собирает бинарник из этого чекаута, создаёт служебную учётную запись
и каталоги, пишет конфигурацию, ставит Caddy как TLS-фронт-прокси, открывает
firewall, запускает обе службы, проверяет релей и записывает учётные данные и
URL моста в файл с правами `0600`, принадлежащий root.

```bash
git clone https://github.com/PalMeany/whatif-telemt.git /usr/local/src/telemt
cd /usr/local/src/telemt
./install-web.sh --hostname proxy.example.com --site /path/to/your/site
```

Запускать от root. Скрипт отказывается угадывать то, от чего развёртывание
ломается незаметно: он не станет придумывать публичный сайт, отвергает
неканоническое имя хоста (имя хешируется в каждую capability моста),
отказывается ставить прямой слушатель MTProto на 443 и считает неудачную
проверку здоровья фатальной. Список опций — `./install-web.sh --help`; всё, что
скрипт пишет, перечислено в рунбуке. За вами остаются шаги 0, 1, 5 и с 11-го:
раскладка портов, DNS и firewall провайдера, сам публичный сайт и выдача
учётных данных пользователю.

Шаблоны фронт-прокси, если настраиваете его вручную:
[Caddyfile.example](contrib/web/Caddyfile.example),
[nginx.conf.example](contrib/web/nginx.conf.example). Оба перезаписывают, а не
дополняют `X-Forwarded-For`, держат таймауты чтения выше периода long-poll,
на отказ бэкенда отвечают коротким телом без баннера вместо фирменной страницы
фронт-прокси и намеренно обходятся без HSTS и сжатия.

## Конфигурация

[`config.toml`](config.toml) в корне репозитория — рабочая отправная точка:
слушатели, режимы, маскировка, пользователи и закомментированный блок `[web]`.
Путь к файлу — единственный позиционный аргумент бинарника.

```
telemt [run|start|stop|reload|status] [OPTIONS] [config.toml]
```

`run` — режим по умолчанию; `start`/`stop`/`status` управляют демонизированным
процессом, `reload` посылает SIGHUP для перезагрузки конфигурации внутри
процесса. Опции `--log-level` (`debug|verbose|normal|silent`), `--silent`,
`--log-file`, `--pid-file` и `--run-as-user` описаны в `telemt --help`;
переменная `RUST_LOG` перекрывает настроенный уровень логирования.
`telemt healthcheck config.toml --mode liveness` — та самая проба, которую
используют контейнерные образы.

Все параметры описаны в
[docs/Config_params/CONFIG_PARAMS.ru.md](docs/Config_params/CONFIG_PARAMS.ru.md),
включая добавленную этим форком секцию `[web]`. Ключи `[web.limits]`,
`[web.timeouts]` и `[[web.profiles]]` разобраны подробно в
[docs/Advanced_settings/WEB_PROXY.en.md](docs/Advanced_settings/WEB_PROXY.en.md)
— этот документ пока существует только на английском.

Issue и pull request по этому форку — в этот репозиторий. Всё, что касается
оригинального проекта, — на <https://github.com/telemt/telemt>.

Патч должен собираться, проходить `cargo test`, быть отформатирован
`cargo fmt` и содержать одно изменение. Правки в транспорте WEB обязаны
сохранять документ моста побайтово идентичным эталонному носителю: закреплённая
сумма SHA-256 в `src/web/bridge.rs` иначе роняет `cargo test`.

Учитывайте, что делает с вкладом §6 лицензии: если вы явно не заявите иного,
отправляя вклад, вы лицензируете его на тех же условиях и предоставляете
описанные в лицензии права как получателям этой программы, **так и
сопровождающим Telemt**. Присылайте только то, что вы готовы отдать на таких
условиях.
